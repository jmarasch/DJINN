# DJINN

Self-hosted, headless party jukebox in Rust. Audio plays on the server's own output devices; guests queue songs from a phone-first web UI.

**`djinn-spec.md` is the source of truth.** Read it before starting new work. Build in phase order and do not start a later phase until the current one meets its acceptance criteria. This file only summarizes spec sections 4, 5, and 16.

## Commands

```sh
# Web UI (required before a release build; debug builds read web/dist from disk)
cd web && npm ci && npm run build      # npm run dev proxies /api to localhost:8066
cd web && npm run check                # svelte-check + tsc

# Rust (same checks CI runs on Linux and Windows)
cargo fmt --all --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
cargo run -p djinn-server -- --config config.example.toml
cargo build --release                  # single binary: target/release/djinn
```

**Branches: `dev` and `main`.** Work is committed straight to `dev` (no PRs); `main` is stable and only moves when `dev` is promoted to a stable release (PR `dev` to `main`, merge, tag). A cron job on the owner's computer starts the Release workflow each night to publish `dev` as a nightly pre-release (GitHub has no schedule of its own; see `docs/releasing.md`, "Stable and nightly"). Claude may commit and push to `dev`; pushing or merging to `main`, and tagging, need the owner's go-ahead every time.

**Weekly rhythm.** Thursday night is cleanup on `dev`, so that night's nightly gives a day of testing. Friday night `dev` goes to `main` as the weekly stable release, unless testing found something to fix first. Thursday cleanup is behavior-neutral only:

- `cargo fmt`, clippy warnings, `npm run check` issues; dead code, unused imports and settings, stale comments.
- This file's code map drifting from the code (files, settings, migrations).
- Em dashes in UI copy, comments and docs.
- Missing tests for queue logic, shuffle bag and transition math (spec section 16).
- Android: hardcoded strings, unused resources.
- Not features, behavior-changing refactors or breaking dependency upgrades.
- Finish with the checks below and a short summary of what changed for Friday's testing.

**GitHub builds only for releases and nightlies.** CI (Linux and Windows) runs on PRs into `main`, at every push to one (PRs into `dev` don't run it; the nightly builds what they merge), a tag runs the release workflow, and the nightly (started from the owner's cron, not by GitHub) builds `dev` (merging doesn't run CI). Don't push work in progress: commit locally, run the checks above locally (they're what CI runs), and push only when it's ready for a nightly or a release. Batch follow-up fixes into that push instead of pushing each one. Test builds for the Windows machine are made locally and sent over the LAN, or come from a published release or nightly.

## Tech stack (spec section 4)

- Rust stable, 2021 edition. tokio runtime, axum for REST + Server-Sent Events.
- Audio: **cpal** for output (WASAPI on Windows, ALSA on Linux), **symphonia** for decoding (mp3, flac, aac, isomp4, vorbis, wav), **rubato** for resampling and drift correction.
- **Do not use rodio.** The engine needs dual-deck decoding, a custom mixer, and fan-out to multiple devices.
- lofty for tags and cover art. SQLite via sqlx with migrations, WAL mode. FTS5 for search. argon2 for passwords.
- tracing + tracing-subscriber for logs. Config is a TOML file plus `DJINN_*` env overrides (figment).
- Frontend: Svelte + Vite + TypeScript, built to static files and embedded in the binary with rust-embed.
- Later phases: notify (fs watching, Phase 2), bliss-audio (similarity, Phase 6).

## Architecture (spec section 5)

```
crates/
  djinn-engine/    audio: decode, mix, outputs. No web, DB, or async runtime deps.
  djinn-library/   scanner, tags, cover art, search
  djinn-store/     SQLite access, migrations, models
  djinn-server/    axum app, auth, API, SSE. Builds the `djinn` binary.
  djinn-cast/      casting: live MP3 stream of the mix, device discovery and control.
  djinn-ai/        optional local models: CLAP (tract, CPU) for song and text embeddings,
                   Qwen2.5 reader (candle) for free-form searches; `djinn-gpu` helper
                   (feature `cuda`, needs the CUDA toolkit) runs it on NVIDIA cards.
  djinn-platform/  OS integration: tray icon, MAC lookup, Windows console. No C deps,
                   so `cargo check -p djinn-platform --target x86_64-pc-windows-gnu` works here.
web/               Svelte app (built to web/dist, embedded by djinn-server)
android/           DJINN GO for Android (Kotlin, Compose, Media3; spec Phase 9). Talks only to GO's port.
migrations/        sqlx migrations
```

- `djinn-engine` must be testable alone via a CLI harness: `cargo run -p djinn-engine --example play -- file.flac`.
- **Threading:** cpal audio callbacks never allocate, lock a mutex, or touch the DB; they only read lock-free ring buffers. A dedicated engine thread decodes and mixes to fill those buffers.
- The tokio side talks to the engine over channels: commands in (`Play`, `Pause`, `Skip`, `SetVolume`, `SetCrossfade`, `SetOutputs`, ...) and events out (`TrackStarted`, `TrackEnded`, `Position`, `Outputs`, ...).
- Queue logic lives in the server, not the engine. The engine asks "what's next?" and is told.

## Where things live

- Engine: `player.rs` sequences tracks and shares one resampling stage across same-rate tracks (that is what keeps resampled albums gapless); with a crossfade it holds back each track's last N seconds and blends them into the next with equal-power curves (tracks marked `gapless`, e.g. the next song on the same album, skip it); `output.rs` owns one device's cpal stream and realtime callback; `outputs.rs` fans audio out to every device: the first open one is the clock the player paces to, the rest follow it through `drift.rs` (a PI controller nudging each follower's resampling ratio by ppm to hold its buffered time, less its delay, equal to the clock's). Per-output delay is applied by padding or skipping audio. On Linux cpal uses its PulseAudio host (covers PipeWire and Bluetooth sinks). `loudness.rs` measures EBU R128 loudness for ReplayGain; `features.rs` describes how a song sounds (tempo, punch, brightness, noisiness, mode, mel cepstrum, chroma: 37 numbers, `analyze` does both in one decode); `Track.gain` is applied right after decoding. `engine.rs` is the thread and command loop. Try outputs with `--example devices` and `--example outputs`. `tap.rs` copies the master stream for casting; with no output open but a tap listening, `outputs.rs` paces playback by the system clock (cast-only). `NextNeeded { after }` names the track the engine just took.
- Accounts: sessions say whether they're an app's (`sessions.device`, migration 35); `CurrentSession` refuses those off GO's port, however the token arrives. Over HTTPS the cookie is `__Secure-djinn_session`, plain HTTP keeps `djinn_session`, and both are read. `users.role` is the kind (admin, user, guest); a `user` account also has a role from `roles` (`djinn-store::roles`: permissions like `go`, `go_remote`, `downloads`, `unlimited_requests`; role 1, Listener, is built in) and a status (active, pending, disabled; only active accounts have working sessions). `auth.rs` handles sign-in, sign-up (`signup_mode` setting: closed, review, open; invite links always work), `/me` (with the role's permissions) and password rules; `accounts.rs` serves roles, sign-up settings, invites (only the token's hash is kept) and signed-in devices; `web/src/lib/UsersPanel.svelte` is Admin > Users.
- DJINN GO: `go.rs` runs GO's own listener (`[go] listen`, default 8067, started and stopped by the `go_enabled` setting) with `router()`: a fixed allowlist of API routes (`ROUTES`: public, setup, listener), a guard that checks the role's `go`/`go_remote` permissions, the home-network check and required two-step sign-in, security headers, `web::go_handler` serving `go.html` (`web/src/go/GoApp.svelte`, a second Vite entry), and `/go/stream/<token>` (song files as they are, via short-lived grants from `/api/go/play/{id}`, limited by `max_streams`). Admin > GO is `GoPanel.svelte` (`/api/go/status`, `/api/go/settings`); the sign-in log is Metrics and logs > Sign-in log (`SignInLog.svelte`, `/api/sign-ins` paged, `DELETE /api/sign-ins?older_than_days=`). `go_allow_remote` must be on for listeners outside home; `go_upnp.rs` optionally maps TCP 443 to an HTTPS proxy on this computer (never GO's HTTP port), on a renewed one-hour lease. `security.rs` works out the client behind trusted proxies (`trusted_proxies` setting; forwarding headers from anyone else count as away from home), `is_home` (private ranges and Tailscale's 100.64.0.0/10), both ports' headers and `same_origin` check, and the `Limiter` (tries per account and address, per address, and per account; two-step codes count apart and a right password doesn't reset them; sign-ins and codes are counted before they're checked; app passwords count under `app:<name>`, API keys by address alone); it also holds the shared `hex`, `random_hex`, `random_text` (letters drawn without bias) and `same_secret` (constant time) helpers, and `NODE_CSP` for a node's own page, which `node_mode::router` sends through `node_headers` and `same_origin` like Main's pages. `auth.rs`'s `HashGate` limits Argon2 running and waiting. Away from home GO refuses sign-ins over plain HTTP unless `go_allow_plain_remote` is on. Song links end with their session; `two_step.rs` is TOTP (RFC 6238), recovery codes and the login tickets; every sign-in attempt goes to `sign_ins` (`djinn-store::security`). Your account page: `AccountPanels.svelte`. Phone apps: `subsonic.rs` is the Subsonic API at `/rest/{method}` on the GO port (a small `Node` tree written as XML or JSON; sign-in with the app password from `subsonic_keys` as plain, `enc:` hex, MD5 token or API key; streaming through `go::send_song`), over `djinn-store::subsonic`; app passwords are `/api/me/app-password` (`go/PhoneApps.svelte`); GO installs as an app via `web/public/go.webmanifest`. Converting (off by default): `convert.rs` (settings, a cache in `<db dir>/converted/` keyed by path, size, mtime and bit rate, trimmed oldest first, a semaphore for jobs at once) over `djinn_cast::convert::to_mp3` (`djinn_engine::decode_stereo` into the live stream's MP3 encoder); GO's play links take `?convert=1` and say `can_convert`, Subsonic's `stream` converts for `format=mp3` or a lower `maxBitRate`; the role permission is `convert`. Submitting music: `submissions.rs` (upload to `<db dir>/uploads/` with a size cap, decode check via `djinn_engine::fingerprint`, tags via `djinn_library::basics`, duplicates by hash and by `same_song`; approval moves the file into `upload_folder` as Artist/Album/file, makes that folder a library root with `folders::ensure_root`, and starts a scan) over `djinn-store::submissions`; GO's `views/Submit.svelte` and Admin's `SubmissionsPanel.svelte`. Favorites in the party app: `likes_api.rs` (`/api/likes`, the same `go_likes`, guests refused by `playlist_api::Member`), `favorites.svelte.ts`, `Heart.svelte`, `screens/Favorites.svelte` (its own nav tab, between Library and Queue, for accounts with playlists). Every song by an artist: `/api/artists/{id}/songs` (`artist_song_page`, also on GO's allowlist) for Play all and the All songs page that Show all opens (`#/artist/<id>/songs`: `screens/ArtistSongs.svelte`, GO's `views/ArtistSongs.svelte`, Android's `ArtistSongsScreen`). A quick skip within `HEARD_RECENTLY_MS` of the same person hearing the song through isn't recorded (`record_go_play_at`; migration 43 cleared older ones). Your own library on GO: `go_library.rs` (routes only work on the GO port via the `GoUser` extractor: home, likes, plays, history, resume, playlists, radio, send to party) over `djinn-store::personal` (`go_likes`, `go_plays`, `go_resume`, `go_playlists`); the GO web app is `web/src/go/` (`player.svelte.ts` runs two audio elements so the next song preloads, shuffle/repeat, ReplayGain as element volume from the play link's `gain`, `canPlayType` on its `mime`, Media Session, history reports and resume saves; `views/` are the screens). `cargo audit` runs in CI; reviewed exceptions are in `.cargo/audit.toml`.
- Finding a server and keeping songs: `go_announce.rs` is the server's name and id (`/api/go/hello`, public) and its mDNS announcement while GO is on; the app's `data/Discovery.kt` lists what it hears. `go.rs` `KeepRules` (`/api/go/keep-rules`, Admin > GO) say what happens to kept songs; the app's `OfflineStore.checkAccess` caches and follows them (`whenAway`, `isLocked`).
- Encryption and several servers: `tls.rs` makes the server's own certificate (`<db dir>/tls/`) and `tls::listen` answers TLS and plain HTTP on one port by peeking the first byte, limits open connections and the time to send a first request's head, and gives `tls::Peer` as connection info, which `client::note_peer` turns into `ConnectInfo<SocketAddr>` and `DirectTls`; the `go_encryption` setting switches it per connection. The app's `data/Servers.kt` is `Account` (saved servers, each with its own token and pin) and the pinning; `GoApi.probe` is the first look at a server. Songs and per-server prefs are keyed by `Account.scope` (server id plus account id), not the address.
- The app from the server: the release workflow builds the APK first and leaves it in `android-dist/` (not in git) for the server build; `go_app.rs` embeds it and serves `/api/go/app` and `/go/app/djinn-go.apk`, both public, on GO's port. Builds without one don't offer it. `web/src/go/GetApp.svelte` offers it on Android, Admin > GO has a QR code, and the app's `data/AppUpdate.kt` fetches newer versions over its pinned connection for Android's installer. `versionCode` comes from the release date in `Cargo.toml`.
- Library extras: a library check is folders and tags only; Admin > Library (`web/src/lib/LibraryExtras.svelte`) switches on sound analysis (`sound_analysis`, off for new installs, migration 26 keeps it on where songs were analyzed), artist photos and bios (`online_artist_info`), MusicBrainz (`musicbrainz` plus its contact; `settings::musicbrainz`, `lookups_on`) and identifying songs (AcoustID key). Artist slideshows (`artist_pictures`, needs photos and MusicBrainz) use cached Wikimedia Commons, fanart.tv, and TheAudioDB images according to source settings; lookups keep each artist's Commons category (Wikidata P373, migration 27). `library_api::pictures_for` fetches sized JPEGs with credits the first time they're wanted (`online::artist_pictures`, one artist at a time), served at `/api/artists/{id}/pictures` and, for the artist playing, `/api/tv/pictures`. The admin can manage images on the artist page, import licensed files, or select Unsplash images for direct remote display when enabled. Migration 28 stores source and remote URL; the art cache has count, size, and resolution limits. `ArtistSlideshow.svelte` shows them. `background.rs` is when heavy work (sound analysis, AI listening) may run: any time, only while no music plays, or between hours (`background_when/from/until`); both loops call `wait_turn` between batches and report `held` in their status.
- Server: `cpu.rs` reads the computer's threads and cores before the runtime starts, sizes analysis and the AI reader from them (the reader's candle pools via `RAYON_NUM_THREADS`/`CANDLE_NUM_THREADS`, always leaving a thread free) and logs them; `desktop.rs` runs the tray (skipped without a display or with `--no-tray` / `server.tray = false`); `banner.rs` picks the LAN URL and prints the terminal QR; `address.rs` keeps it current (`AppState::join_url` is a `JoinUrl`, checked every 10 s with 0.0.0.0 listening; a change sends `ServerEvent::Address`, rewrites the console banner, restarts casts via `cast_api::recast`, and for `ANNOUNCE_AFTER_MOVE` announces GO and Main even when hidden (`JoinUrl::moved_lately`); the Android app's `ServerSeeker` (`data/Discovery.kt`, started by `GoApi.onUnreachable`) then hears it by id and follows it with `Account.moved`, pinned servers only); the library check runs in the background after the server is listening. `jukebox/` decides what plays (requests first, then the auto mix in `jukebox/auto.rs`: the active playlist by shuffle bag or in order, wild play, or radio), tracks queued, in-flight, and playing tracks, keeps `planned` (the auto mix's next `PLAN_AHEAD` songs after `queued`, drawn with `draw_after` so they count as played; a request that bumps a pool pick puts it back at the front; cleared when the active playlist changes; shown as `NowPlaying.later`, at most `PLAN_AHEAD` of them; nodes ask for more with `plan_for_nodes`, up to their `cache_ahead`, for `PLAN_WISH_SECS`), and counts skip votes (in memory, reset per song); its tests are in `jukebox/tests.rs`. Asking for a song already queued makes you a backer (`request_backers`): it uses one of your slots, and the queue plays songs with more backers first, then in request order (`queue_order!` in `djinn-store::queue`, worked out on read; admin moves stay among songs with as many backers); a requester who steps back hands the request to the first backer; `playlist_api.rs` manages playlists; `cast_api.rs` serves the live stream at `/cast/<token>/live.mp3` (ICY "Artist - Title" for players that ask; a token instead of a session, since devices fetch it themselves; `djinn-cast::stream` encodes it and fills pauses with silence), its token is handed out only by Play here, a cast's own address (`/tv?cast=<token>`) and the TV page when `tv_sound` is on, and `/api/cast/new-link` changes it; Play here (`/api/listen` hands the stream URL to anyone signed in while the `play_here` setting is on; `web/src/lib/playHere.svelte.ts` plays it, reconnects, and sets the lock-screen Media Session) and the admin cast API; `djinn-cast` finds devices (`discover.rs`: mDNS for Google Cast, SSDP on every interface for DLNA/Sonos, since a VPN steals default multicast), plays to them (`cast.rs`: CASTV2 with the Default Media Receiver for audio, or DashCast to show the TV page (`/tv?cast=1`, which plays the stream itself); `upnp.rs`: AVTransport SOAP, Sonos via `x-rincon-mp3radio`), and `caster.rs` keeps each cast alive with retries; active casts resume after a restart (`cast_targets` setting); try `--example discover` and `--example probe <ip>` (both read only); `tv_api.rs` serves the public, read-only TV page feed (`/tv`, gated by the `tv_page` setting); `audio_api.rs` manages outputs and ReplayGain, and measures loudness of untagged songs in the background after each library check while ReplayGain is on; background work after a check runs in phases: the scan (`ScanPhase`: finding, reading, sorting), then sound analysis, then AI listening (which waits while analysis runs; analysis starts it when done), with online lookups alongside; `/api/library/status` carries all of it for the Library tab's `LibraryProgress.svelte`; try a big library with `cargo run --release -p djinn-library --example fake_library -- <dir> 36000`; `jukebox/gain.rs` turns tags or measurements into a track's gain; `folders.rs` handles library folders (config.toml plus ones added in the app) and the folder browser; `events.rs` + `sse.rs` push live state; `*_api.rs` are the REST routes; `settings.rs` reads and writes admin settings (`number`, `flag`, `set_flag`), and each setting's name lives with its feature.
- Library: `online.rs` looks up artist photos (Deezer, then Wikimedia Commons with credit) and bios (Wikipedia) when the admin turns it on, plus MusicBrainz (exact artist/album matches, genres, Cover Art Archive covers) once a contact is set; strict matching, MusicBrainz paced to 1 request/s, retries. Automatic lookups (after a library check that found changes) only cover artists and albums not looked up yet; "Recheck all" redoes everything. Everything found is cached in `<db dir>/art/` as `<hash>.<ext>`; the music library itself is read-only.
- Smart playlists: the background analysis job (`audio_api::start_analysis`) stores features per track; `djinn-library::sound::SoundIndex` (weighted z-scores, tuned on a real library) answers "more like this" and similar artists; `smart.rs` keeps it in memory with song facts (years, genres from tags plus MusicBrainz, popularity) and serves `/api/tracks/{id}/similar` and `/api/artists/{id}/similar` (genre overlap plus sound). `djinn-library::vibe` reads descriptions ("80's hair metal", "chill house", "upbeat like KREAM") into an intent and ranks songs; search returns them as `described`.
- Importing playlists: `djinn-library::playlist_file` reads exports (CSV/TSV by header names, Spotify JSON, JSPF, XSPF, Apple XML, M3U, PLS, pasted lines), `playlist_match::SongIndex` finds them in the library (strict: version notes like "Remastered" don't count, "Live" does; artist must overlap), `playlist_import.rs` is `/api/playlists/import` and the file checks. `youtube.rs` reads YouTube playlist links through the official Data API with an admin's key (`youtube_api_key`); it must stay strictly one way (only the key and list id, no user agent, referrer, cookies or redirects, key in a header), and `it_says_only_which_list_and_the_key` holds it to that. Video ids in files are never sent. Other services' links aren't read. Songs the library lacks are entries of kind `wanted` (`playlist_wanted`), never played, filled by `fill_gaps` after a library check that changed something, which also repoints entries whose file moved. Files that won't play go in `track_problems` (not `tracks`, so scans and browse triggers don't notice): `note_failure` records them from the engine's `TrackError` or a **Check files** run (`djinn_engine::verify`, a whole decode), a changed size or mtime clears them in `save_track`, and `after_library_check` retries them. Playlist expansion (`covered!` in `djinn-store::playlists`) has one branch per kind so large imports stay fast. Admin > Library > Problems is `problems_api.rs` over `djinn-store::problems` (`ProblemKind`): what the walk couldn't add (`scan_problems`, migration 38, replaced by every check), unreadable tags (`ScannedTrack.tag_problem`, written by `save_track`), `track_problems`, and tag gaps worked out on read; hidden kinds are the `problems_hidden` setting; listeners' reports (`song_reports`, migration 40, `POST /api/tracks/{id}/report`, also on GO's allowlist; `ReportSong.svelte`, Android's `ReportDialog`) are the `reported` kind; the page is `LibraryProblems.svelte`. `scheduled_check.rs` is the optional nightly check (`scheduled_check`, `scheduled_check_hour`; runs once a day from its hour, then saves a `Summary` against the last one; `ScheduledCheck.svelte`). Possible duplicates: sound analysis also keeps the start of each song's Chromaprint fingerprint (`Analysis.print`, `track_sound.print` with its own `PRINT_VERSION`, migration 39, so the features stay valid); `djinn-library::duplicates::find` groups songs by core title and artist (playlist_match's rules), applied AcoustID recording, or print similarity (`djinn_engine::print_similarity`), with sound vetoing namesakes and the keeper first; `duplicates.rs` (server) caches the groups until `duplicates_version` changes and serves `/api/library/duplicates`; `duplicate_dismissed` holds pairs marked not copies; the card is `LibraryDuplicates.svelte`. The jukebox gets them through the `Copies` trait (`duplicates::KnownCopies`, never waiting; `duplicates::refresh` after library checks and analysis): `auto.rs` `recent` puts each recent song's copies right after it (`avoid_copies` setting).
- Playlists: one system for the party, GO and phone apps (`playlists`, `playlist_entries`, `playlist_shares`; migration 32 merged `go_playlists` into it, GO's ids kept). A playlist is private to its owner until shared with everyone (`shared`) or particular people, never with guests (`playlist_api::Member` keeps guests out, `must_own` guards changes, admins get no special access). `/api/playlists` is the party app's view; `/api/go/playlists` keeps its shape for GO, phones and `subsonic.rs` (`personal.rs` wrappers), and GO's allowlist adds import, the YouTube key's status, sharing and removing an entry. `set_playlist_songs` applies an app's flat song list without losing what it can't express. `PlaylistDetail.rows` lays the list out in order with flags, for GO and the phone. Starting one as the auto mix needs the `auto_mix` permission.
- Radio and learning from the party: `jukebox/mix.rs` holds `RadioSeed` (song, artist, genre), the `Mixer` trait, `party_weight` (requests up, "play less" skips down: a plain skip counts for nothing since it may only mean wanting the next song; `play_events.play_less`/`go_plays.play_less`, migration 51, is 1 when someone chose "Skip, play less" (`/player/skip?less=1`, GO's play report `play_less`) and 2 when the room's skip votes sent the song away, which counts double; `plays_since` and `go_play_less_since` feed radio the same way), `Learned` (what one party style liked, per song, artist and genre, from `SongLinks` the mixer supplies) and the weighted draw; wild play and radio draw by weight, playlists keep the shuffle bag (ordered by weight with `smart_playlists`). Party styles (`djinn-store::party`, `party_api.rs`, Admin > Smart play): requests and plays record the style in use (`style_in_use!`), clearing a style detaches its events from learning but keeps the request log; `smart_play`, `smart_playlists` and `smart_strength` settings. The PC disc asks for the box's name (`djinn` suggested) and installs SSH for the maintenance login; Pi images get SSH and a name from Raspberry Pi Imager. The PC disc's boot menu also offers "with a screen" (`djinn_screen=1`: `preseed/early_command` adds the kiosk packages to the software step, `pc/late.sh` runs `common/kiosk.sh`: cage plus Chromium in kiosk mode, `djinn-screen.service`, opening `/screen`, which is the not-set-up page (`NotSetUp.svelte`: message, link and QR from `/api/auth/bootstrap/qr.svg`, also what `/` shows) until set up, then `/tv`; on a node `/node?screen=1`, then Main's TV page from `Status.screen`). Pi builds: `djinn-linux-aarch64` (GitHub ARM runner) and `djinn-linux-arm` (ARMv6 via `cross`, `Cross.toml`; tract's NEON kernels mark it v7 but are only used when present); `install.sh` picks the tarball by `uname -m`.
- The look (after `imagery/layout concepts`, kept outside git): `app.css` tokens (`--edge`/`--edge-strong` and `--glow`/`--glow-strong` give the neon edges, `--card-bg`, `--page-bg`, `--accent-2` teal), the Outfit font bundled from `@fontsource-variable/outfit`, `Logo.svelte` (the DJINN icon image, `public/images/logo*.webp`; app icons are the same picture), `Brand.svelte` (logo, name, tagline `brand.tagline`), `PageTitle.svelte` (a big title between waveforms). `App.svelte` is the frame: a header (logo, room picker, Join, a menu for Playlists, account and Admin) with Playing, Library, Favorites and Queue along the bottom on phones; from 900 px the same `nav.side` is a side menu, shrunk to icons (`rail`) on Admin pages. Placeholder and empty-screen pictures are in `public/images/` (`Art.svelte` shows `missing-album`/`missing-artist` when a picture is missing). The tray draws its own mark in `tray.rs`; the Linux menu entry names its icon by full path so desktops don't keep a cached one.
- Translations: `web/src/i18n/<lang>.json` (English is the reference; Spanish, French, German so far), `t()` in `web/src/lib/i18n.svelte.ts` (`{name}` placeholders, `{one, other}` plurals via Intl.PluralRules, falls back to English), the language picked on the device (`LanguagePicker.svelte` in `AccountPanels`, so the party app's and web GO's account pages; Android's Settings, `Prefs.language`), else the house default (`language.rs`, the `default_language` setting, Admin > System > Language, public `/api/language` on both ports; Android keeps it as `Prefs.houseLanguage` from each sync), else the phone's own. Guest-facing party screens and web GO's main screens (nav, home, search, library) are translated. Android reads the same files (copied into its assets as `i18n/<lang>.json` by the `copyTranslations` Gradle task) through `i18n/Strings.kt` (`t(key, "name" to value)`, `Strings.load` in `DjinnApp` and `MainActivity` and again when the choice changes); every Android screen, notification and Auto folder is translated (lists of choices hold translation keys, shown with `t(label)`; unit tests that check wording call `Strings.useEnglish` with `web/src/i18n/en.json`). - Store: one module per area (`library`, `playlists`, `users`, `queue`, `outputs`, `loudness`); all SQL is static strings (sqlx 0.9 rejects dynamic SQL), with shared column lists as macros used through `concat!`.
- Android app: `data/GoApi.kt` is the API client (its one OkHttp client adds the Bearer token, only for the signed-in server); `player/PlaybackService.kt` is the Media3 service: items are `djinn://track/<id>`, resolved to a fresh play link only when the cache lacks them, with the song (not the link) as cache key, and it reports plays and resume; `player/CacheAhead.kt` fetches the queue's next few songs (`Prefs.cacheAhead`, Settings > Storage) into that cache, one at a time; `player/PlayerState.kt` is the screens' view of it (songs carry their artist and album ids in metadata extras, read by `MediaItem.artistId`/`albumId`; another server's kept songs have none); `ui/` is Compose, laid out like web GO: tabs Home, Library (`SearchScreen`, which shows `LibraryScreen`'s browse tabs while nothing's typed), Your music (`YourMusicScreen`: Liked, Playlists, History, Your year, On phone) and Account (`SettingsScreen`). `ui/Browse.kt`'s `PagedList` keeps each row at its place in the whole list and loads pages around the screen, so `ui/JumpStrip.kt` can jump anywhere. Apps sign in with `device_token` in the login body and get a token that only GO's port accepts (`auth::request_token`). Android 16+ needs `ACCESS_LOCAL_NETWORK` to reach a server at home, requested in `MainActivity`. Kept songs: `data/Offline.kt` (Room, plain files in `files/offline/<server hash>/`, system sounds through MediaStore, pending plays and likes), `work/Workers.kt` (downloads, smart cache, sync), over `/api/go/offline/{id}` (`go.rs`: needs `downloads`, doesn't count as a stream, converts lossless to MP3 with `kbps` and `vbr`), `/api/go/offline/versions` and `/api/go/offline-suggested`. `player/Spectrum.kt` is the visuals' analysis (`SoundReader` is what a style reads each frame, on a steady clock), `ui/Visuals.kt` the shape styles and full screen, `ui/MoreVisuals.kt` the styles ported from the web's `nodeVisual.ts` (Spectrogram, Scope, Mountain, VU, Circle, Particles, Terrain, Flyover; change both; `SoundReader` carries left, right and `needles` for them), `ui/GlVisuals.kt` the shader styles (OpenGL ES 2; add a style to the end of `VisualStyle`, since it's stored by position); `player/Cast.kt` casts the queue with Google's default receiver; `PlaybackService` is a `MediaLibraryService`, so its tree is what Android Auto browses; other apps get buttons only (`onConnect`, `Controllers.kt`). Work a song menu starts uses `nav.scope`: the menu's own scope ends when it closes.
- Golden-sample audio fixtures: `crates/djinn-engine/tests/fixtures/` (README says how to regenerate). Acceptance checklists and test notes are kept locally in `notes/`, which is not in the repository.

## Coding rules (spec section 16)

- No `unwrap()` or `expect()` outside tests and startup config validation. Enforced by workspace clippy lints (`clippy.toml` allows them in tests). Use `anyhow` in binaries and `thiserror` in library crates.
- Nothing on the audio callback thread may allocate, block, or log.
- Every DB change goes through a migration.
- Keep `djinn-engine` free of web, DB, and async runtime dependencies.
- Write tests for queue logic, shuffle bag, and transition math. Gapless needs a golden-sample test: two test tracks concatenated through the engine must have no gap or click at the boundary.
- Do not use em dashes in UI copy, comments, or docs.
- Exit 66 Jukebox (Go + Svelte rewrite) has no license: use it for ideas only, never copy code.
